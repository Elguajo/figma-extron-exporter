## Рекомендации, не меняющие результат

### P1. Не вычислять подпись дизайна, которую никто не читает — плагин

`captureSingle()` в конце всегда вызывает `designSignature(root)`. В двух местах результат выбрасывается:

- `captureProject()` (`project.ts`) берёт у каждого экрана только `screen` и `images`; поле `signature` участника не используется, подпись проекта считается отдельно;
- `recognize()` (`recognize.ts`, вызов `capture(root, read, …)` перед `plan.registry`) вызывает захват только ради проверки: возвращаемый `Capture` отбрасывается целиком.

**Что сделать:** добавить в `capture` и `captureSingle` необязательный флаг «без подписи» и передавать его в этих двух вызовах. Для `applyRecognition` и `exportCaptured` всё остаётся как есть: их подпись защищает от правок во время экспорта.

**Эффект:** клик по слою — 3 → 1 снимок; проверка проекта — 9 → ~4; экспорт проекта — 11 → ~6. Бандл и сообщения те же.

**Риск:** низкий. Проверка — существующие тесты и `test/startup-benchmark.ts`: он уже сравнивает бандл «до/после» через `deepEqual`.

### P2. Не запускать `publish()` с повторным распознаванием посреди экспорта — плагин

`exportRoot()` вызывает `publish()` после `applyRecognition`, ещё до PNG-экспорта. Внутри `publish()` для проекта снова выполняется `recognize()` — полный проход с захватом, хотя только что применённый план уже есть. Отсюда 2–3 лишних снимка на каждый экспорт.

**Что сделать:** передавать в `publish()` уже готовый план, чтобы `preparedLinks` не пересчитывался. После `applyRecognition` он равен свежему `recognize()`: записи применены, `writes` пусты.

**Риск:** низкий–средний. Нужен тест, что сообщение `selection` после экспорта не изменилось.

### P3. Кэшировать поиск полей в хосте — `ExtronAdapterHost.ps1`

`Find-TypeField` при каждом `Get-F`/`Set-F` заново проходит иерархию типов через `GetField(..., DeclaredOnly)`. Пара «тип + имя поля» за время работы процесса не меняется.

**Что сделать:** хэш-таблица `$script:FieldCache["$($Type.AssemblyQualifiedName)|$Name"]`, где хранится и отрицательный результат (`$null`). Сообщения `Fail` в `Get-F`/`Set-F` и чтение назад (read-back) в `Set-F` не трогать.

**Эффект:** оценочно 1,5–2,5 с из 10,7 с на большом проекте.

**Риск:** низкий. Критерий приёмки — SHA-256 `.gdl` совпадает на `examples/exui-v5/*.exui` и на большом пакете.

### P4. Не перебирать ресурсы донора для каждого состояния — `Set-Font`

`Set-Font` для каждого состояния каждой кнопки заново фильтрует все ресурсы проекта через `Items | Where-Object` и регулярное выражение по имени. Это главный источник тех 22 тыс. поисков полей. К моменту вызова `Set-Font` набор ресурсов уже окончательный: `Add-ImageResource` и `Add-EmbeddedFonts` выполняются раньше.

**Что сделать:** один раз построить индекс `PBFontResource` по имени, точному и по семейству, и брать совпадение из него. Порядок кандидатов должен остаться прежним: используется `$match[0]`.

**Риск:** низкий; критерий приёмки тот же — SHA-256 `.gdl`. Похожие места: поиск `Slider Thumb` в `New-PlanControl` и проверка конфликта имён в `Add-ImageResource` (сложность O(изображений × ресурсов)).

### P5. Мелочи без влияния на результат

- `exportPng()` (`read-node.ts`) для каждого PNG пересчитывает правую границу всех узлов страницы: `figma.currentPage.children…map(n=>n.x+n.width)`. При 100 PNG и сотнях узлов верхнего уровня это заметно. Значение можно посчитать один раз на экспорт; функция места размещения временного клона это не меняет.
- `Read-Payload` и `Test-AdapterContract` создают `SHA256` без `Dispose`. На утечку это не влияет, процесс короткий, но поправить дёшево.
- `dist/code.js` собирается без минификации: 569 КБ, из них ~100 КБ — встроенный UI. Минификация ускорит разбор при запуске на единицы–десятки миллисекунд. Сообщения не изменятся, но изменятся стеки ошибок, поэтому это самый низкий приоритет.

## Стабильность: найденные дефекты

### S1. Повреждённые данные слоя «замораживают» панель плагина — подтверждено

**Воспроизведение:** в слое `screen_Main` или `popup_Sources` записать `exui = "{corrupt"` и выделить его. `publish()` выбрасывает исключение «повреждены данные Extron», сообщение `selection` в UI не уходит, и панель продолжает показывать предыдущий выбор.

Задуманное поведение было другим: `publish()` ловит эту ошибку и показывает её как `warning`, чтобы назначение можно было исправить вручную. Однако вызов `popupBindingInfo(...)` стоит прямо в литерале `postMessage` вне `try`. Его первая строка `selection.every(n => selectionKind(n))` читает метаданные без защиты.

**Что сделать:** обернуть вычисление `popupBinding` в `try` по образцу соседних полей. Дополнительно — внешний `try` вокруг всего `publish()`, который при любой непредвиденной ошибке отправит минимальное сообщение `selection` с `warning`. Для корректных данных поведение не меняется. Тот же путь проходит `ready`: при открытии плагина на таком слое UI остаётся в стартовом состоянии.

### S2. Сообщение «ошибка» после успешной записи `.gdl` — `PackageGenerator`, `ExuiPackage`

`finally { Directory.Delete(stage, true); }` в `PackageGenerator.Generate` и `ExuiPackage.Dispose()` удаляют временные папки без перехвата исключений. На Windows антивирус или служба индексирования часто на мгновение удерживают только что записанные PNG или `.gdl`. Тогда возникает такой сценарий:

1. `.gdl` и `.report.json` уже перемещены на место;
2. удаление папки выбрасывает `IOException`;
3. CLI печатает `ERROR:` и возвращает 1;
4. повторный запуск с тем же именем отказывает с `output-exists`.

В `ExtronAdapter.Execute` это уже сделано правильно: `try { Directory.Delete } catch (IOException) {} catch (UnauthorizedAccessException) {}`. **Что сделать:** применить тот же шаблон в двух местах, а также в ветке `catch` метода `ExuiPackage.Load`, где ошибка удаления маскирует исходную ошибку.

### S3. Необработанные типы исключений в CLI — `Program.cs`

Общий `catch` перехватывает `IOException`, `InvalidDataException`, `UnauthorizedAccessException`, `ArgumentException`, `NotSupportedException` и `SerializationException`. Мимо него проходят:

- `JsonException` — если `result.json` хоста повреждён или обрезан, например при убитом процессе;
- `InvalidOperationException` — `result["ok"]?.GetValue<bool>()` при неверном типе значения; `process.Kill()`, если хост завершился между таймаутом и `Kill`.

Пользователь получает аварийное завершение .NET со стеком вместо `ERROR [code]: …`. Код возврата всё равно ненулевой, поэтому `ExtronExporter.ps1` не сломается. **Что сделать:** добавить эти два типа в существующий фильтр `catch` (с выводом `ERROR:` и кодом 1). В `ExtronAdapter` обернуть `Kill` в `try` и разбор `result.json` — в `AdapterException("host-failed", …)`.

### S4. `selectionchange` во время асинхронных операций — плагин

Флаг `busy` защищает только `onmessage`. Во время `await` в экспорте PNG, при создании Kit (`kit.ts` сам меняет `selection`), в демо и в нумерации событие `selectionchange` запускает полный `publish()` на наполовину построенном дереве. Тот выполняет распознавание, `scopeContext.persist()` пишет данные страницы, а `recognition = undefined` сбрасывает отчёт.

Сейчас это проявляется как лишняя нагрузка и промежуточные обновления UI, а не как порча данных: снимок экспорта не включает `PAGE_SETTINGS_KEY`. **Что сделать:** пока `busy`, только запоминать, что обновление нужно, и выполнить один `publish()` в `finally` после `idle`. Риск средний: UI обновится после операции, а не во время. Синхронные тесты с `f.emit('selectionchange')` вне операций не затрагиваются.

### S5. Конвейер выпуска зависит от незакоммиченных файлов

Изменённые файлы ссылаются на неотслеживаемые (`??`):

| Изменённый файл | Требует неотслеживаемый |
|---|---|
| `src/adapter/Extron.Adapter.csproj`, `ExtronAdapter.cs`, `Program.cs` | `src/adapter/Compatibility.cs`, `compatibility/extron.json` |
| `scripts/Package-Release.ps1` | `docs/extron-compatibility.md`, `compatibility/extron.json` |
| `src/figma-plugin/package-plugin.mjs` | `design/extron-kit/icons/LICENSE` |
| `src/figma-plugin/src/kit.ts` | `src/figma-plugin/src/kit-patterns.ts` |
| `tests/format/Program.cs` | `tests/format/CompatibilityTests.cs` |

Частичный коммит любой из этих пар даёт чистый checkout, который не собирается или не упаковывается. Коммитить связанные файлы вместе. Перед выпуском прогонять `Package-Release.ps1` на свежем клоне.

### S6. Мелкие риски

- **Таймаут хоста 10 минут.** Даже на проекте предельного размера хост работает около 12 с, поэтому при зависании пользователь ждёт 10 минут без вывода. Можно сделать значение настраиваемым через переменную окружения, сохранив прежнее по умолчанию.
- **Временные папки при Ctrl+C.** `%TEMP%\exui-package-*` и `%TEMP%\extron-adapter\<guid>` остаются при прерывании, а вторая содержит копию донора. Можно при запуске удалять такие папки старше суток. Это новое поведение, поэтому низкий приоритет.
- **Память UI при упаковке.** Бандл с PNG до 16 МиБ копируется 3–4 раза: structured clone, `new Uint8Array` в `packageExui`, ZIP, `new Uint8Array` для `Blob`. Пик ~64 МиБ — допустимо; лишние копии можно убрать без изменения байтов архива.
- **Перебор всей страницы при каждом выделении.** `presetSources()` (`button-preparation.ts`) при каждом выделении обходит всю текущую страницу, если образцы не назначены явно. Это уже частично оптимизировано и покрыто `startup-performance.test.ts`; кэширование между событиями потребует инвалидации, поэтому сейчас не рекомендуется.

## Что не рекомендуется без отдельного решения

- **Дебаунс `selectionchange` (50–100 мс).** Даёт наибольший выигрыш при перетаскивании рамкой выделения, но меняет сроки сообщений. Ломает тесты, которые проверяют сообщения сразу после `emit` (`startup-performance.test.ts`, `selection-actions.test.ts`).
- **Мемоизация `readMetadata` по строке JSON.** `recognize` изменяет полученные объекты (`delete m.popup`), поэтому общий объект из кэша опасен, а клонирование съедает выигрыш.
- **Параллельный `exportAsync` для PNG.** Меняет порядок сообщений прогресса и пиковую память в Figma; выигрыш на реальном хосте не подтверждён.
- **Замена `Copy-Graph` (BinaryFormatter round-trip) на собственное клонирование.** Именно эта техника проверена с GUI Designer 1.28.0.7; результат обязательно сравнивать по SHA.

## Порядок внедрения

1. **S1, S2, S3** — исправления стабильности: несколько строк каждое, поведение при корректных данных не меняется.
2. **P1, P3, P4** — оптимизации с объективным критерием: совпадение бандла (`startup-benchmark.ts`) и SHA-256 `.gdl` на `examples/exui-v5/*.exui`.
3. **P2, S4** — после добавления тестов на сообщение `selection`.
4. **S5** — при ближайшем коммите текущих изменений.
