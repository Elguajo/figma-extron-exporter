# README похожих продуктов: исследование 24 октября 2026

## Вывод

Для Figma → Extron Exporter наиболее полезна комбинация трёх подходов: структура пользовательского README из **Figma to Code**, демонстрация исходника и результата из **RedMadRobot FigmaExport**, точное обозначение проверенной среды и доказательств из **extron-gdl-toolkit**.

Главное улучшение нашего README — быстрее показать результат и довести читателя до первого успешного экспорта. Технического материала уже достаточно; при переработке нужно изменить порядок и распределение материала, сохранить проверенные ограничения и убрать историю изменений из установки.

«Лучшие» здесь означает наиболее полезные редакционные решения для нашего проекта, а не рейтинг популярности или качества самих продуктов. Прочитаны семь README из текущих веток по умолчанию. Оценивались текст, структура, ссылки и включение демонстрационных материалов; сторонние продукты не устанавливались, видео и достоверность рекламных заявлений отдельно не проверялись. README нашего проекта не изменён.

## Какие решения взять

### 1. Начинать с результата

Сохранить точное описание нашего продукта: подготовленный интерфейс Figma превращается в редактируемый GDL с нативными контролами и постоянными ID. Сразу показать маршрут `Figma → .exui → .gdl → GUI Designer` и заметную ссылку скачивания совместимой пары плагина и CLI.

Рядом нужен реальный пример: один экран в Figma и тот же экран после открытия в GUI Designer. Подпись должна объяснять, какие элементы редактируются нативно и что остаётся графикой. Если используется GIF, он должен показывать действие и результат. Это адаптация приёма `Result` из RedMadRobot, а не повод создавать декоративный баннер.

### 2. Показывать два пути первого знакомства

- **Проверить готовый пакет:** скачать CLI → проверить включённый EXUI → увидеть ожидаемый отчёт; затем при наличии Extron и донора получить GDL.
- **Экспортировать свой экран:** установить плагин → взять готовый шаблон/Extron Kit → подготовить экран → проверить и скачать EXUI → конвертировать → открыть в GUI Designer.

В каждом пути назвать вход, действие и ожидаемый выход. Не обещать время прохождения без измерения на новой установке. Не смешивать установку инструмента с настройкой логики управления.

### 3. Требования к исходнику сделать частью контракта

В README оставить один минимальный пример структуры экрана и несколько имён: `screen_Home`, `button_Mute`, `slider_Volume`, `value_Volume`. Полную таблицу префиксов, подготовку состояний и правила типографики дать ссылками на существующие документы.

Это особенно важно для нашего продукта: наличие слоя в Figma само по себе не означает, что он будет экспортирован в нужный тип Extron. Полезный образец — явный раздел `Design requirements` у RedMadRobot и примеры семантических имён у FigmaQML.

### 4. Отделить результат экспорта от AV-логики

Объяснить, что получает дизайнер и что передаёт программисту: GDL, отчёт и карта ID. Прямо обозначить, что команды управления и feedback настраиваются отдельно, а повторный экспорт и обновление настроенного GCP требуют своего рабочего процесса.

Ограничения должны помогать решить, подходит ли инструмент: поддержанные панели и версии, правила подготовки, зависимость от доноров, границы сохранения ручных изменений. Это сильная сторона Figma to Code и предметно важная часть README extron-gdl-toolkit.

### 5. Сделать README входом в документацию

Существующие документы уже владеют подробностями: префиксы, стандарт макета, состояния кнопок, Extron Kit, обновление GCP, контракты EXUI и формат GDL. Нужен короткий указатель по задачам. Историю версий оставить в CHANGELOG, выпуск и подробную архитектуру при будущей переработке можно вынести в документы для разработчика.

## Предлагаемый порядок разделов

1. Название и одно предложение о результате.
2. Реальный пример «Figma → GUI Designer».
3. Скачать выпуск · Быстрый старт · Документация.
4. Кому подходит, поддержанные панели и проверенная среда.
5. Быстрый старт на комплектном EXUI с ожидаемым результатом.
6. Свой экран: шаблон → подготовка → экспорт → конвертация → проверка.
7. Что получается и что передать программисту.
8. Ограничения и повторный экспорт; ссылка на обновление GCP.
9. Короткий troubleshooting и указатель документации.
10. Разработка: краткая архитектура, проверенные команды, ссылки.
11. Статус проверки и применимые сведения о лицензировании и происхождении кода.

Это рабочая архитектура для дальнейшей редакции, а не обязательный шаблон. Верх страницы должен отвечать на три вопроса: что получится, подходит ли это моей среде, с чего начать.

## Что проверить перед переработкой

- Подобрать реальные изображения одного и того же экрана в Figma и GUI Designer. Существующие preview Extron Kit показывают дизайн; сами по себе они не подтверждают результат экспорта.
- Проверить быстрый старт именно с файлами последнего публичного архива, включая пути, EXUI и ожидаемые значения отчёта.
- Уточнить доступный пользователю путь получения обязательных доноров; назвать необходимые файлы до запуска конвертации.
- Сверить совместимую пару плагина и CLI, версию GUI Designer и границы проверки на устройстве.
- Проверить права и происхождение материалов перед формулировкой лицензии; не выводить лицензию всего проекта из наличия отдельных сторонних notices.
- Если в README появятся заявления об офлайн-работе или отсутствии отправки данных, подтвердить их manifest и реализацией всех участвующих компонентов.

Для данного исследования сборка и тесты продукта не запускались: код и действующий README не менялись. Поиск включал общие аналоги экспорта Figma, инструменты Qt/embedded GUI и ранее найденный Extron toolkit; он не доказывает полноту рынка или отсутствие закрытых аналогов.
