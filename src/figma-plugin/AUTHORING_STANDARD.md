# Стандарт подготовки макета Figma → Extron, v2.4

Уточнён 22.10.2026. Плагин 0.5.1 preview, стандарт 2.4. Все макеты экспортируются в `.exui/5`, текущий комплект использует CLI 0.5.1. Старые пакеты нужно экспортировать заново; назначения и ID в Figma сохраняются. [Полная таблица префиксов и объяснений](PREFIXES.md).

В 0.3.5 **«Скачать .exui»** и **«Проверить макет»** сами заполняют ключи и свободные ID для новых элементов, копий и конфликтующих назначений. Ручная форма нужна только для особых свойств. Диапазон регуляторов по умолчанию — 0–100; сохранённый диапазон и остальные свойства остаются прежними. Предварительное распознавание — необязательный способ проверить назначения до записи.

## Проект без секции (плагин 0.3.3)

Выделить несколько Frame экранов на открытой странице → «Что экспортировать: Выбранные фреймы — один проект» → «Скачать .exui». Обёртка не нужна. Только выбранные экраны получают назначения и входят в пакет; имя проекта берётся из имени файла, первая страница в порядке выделения — стартовая. Выбранный набор сохраняется при настройке отдельных элементов до закрытия плагина или смены страницы.

Вариант «Экраны текущей страницы» включает только имена `screen_`, `scr_`, `Home` и назначенные страницы размера выбранной панели; служебные данные реестра записываются на открытую страницу. Другие страницы документа не сканируются. Popup и их группы добавлять явным выделением либо экспортировать в прежнем контейнере. Старые уникальные ID и назначения сохраняются; копии и совпадения исправляются автоматически.

С 0.4.3 Corner radius внешнего Frame экрана является оформлением холста Figma и не переносится в Extron. Можно оставить общие или разные радиусы углов и Clip content; плагин не меняет исходный Frame, экспортируемая страница всегда прямоугольная. Это исключение не меняет правила кнопок, фигур, popup и остальных свойств экрана.

## 1. Подготовка и экспорт

1. Для одного экрана создать Frame `Home`, `scr_Home` или `screen_Home` точного размера панели.
2. Для нескольких экранов создать секцию Figma с любым именем либо внешний Frame `project_Trilliant` / `prj_Trilliant`. Непосредственно внутри — Frame страниц, popup и групп popup. Вложенные секции и произвольные подписи вне страниц не поддержаны. Размер и оформление контейнера проекта не экспортируются.
3. Назвать элементы по таблице префиксов. Регистр букв не важен. Короткие и полные варианты равнозначны.
4. Выбрать внешний Frame и профиль. Для автоматической подготовки достаточно проверки или скачивания. При необходимости заранее посмотреть назначения: «Распознать по именам» → проверить таблицу → «Сохранить распознанные назначения».
5. Дополнительные свойства задать через «Назначение выбранного элемента»: диапазон, направление, формат даты, стартовая страница, цель перехода (выбрать страницу по имени), цель popup и указания поведения.
6. «Проверить макет» → «Скачать .exui» → `validate-package` → `convert-package` → проверить копию нового GDL в GUI Designer. Build выполняет пользователь.

Распознавание сохраняет только metadata и резерв ID. Оно не исправляет оформление, не переименовывает и не перемещает слои. Одного переименования без сохранения назначений недостаточно. Произвольные Figma variants, instances, component sets, Auto Layout-поведение и prototype interactions не экспортируются автоматически.

## 2. Профили и геометрия

| Профиль | Размер страницы и модального popup |
|---|---|
| TLP Pro 1025M | 1280×800 |
| TLP Pro 300M portrait | 320×480 |

Каждая страница точно совпадает с профилем. Обычный popup может быть меньше холста. Координаты и размеры нативных элементов — целые пиксели. Для растеризуемой графики и статического текста допустимы дробные значения: PNG имеет целые внешние границы, исходный слой сохраняет точные размеры и смещение внутри них. Элементы внутри своего контейнера, без поворота, skew и отражения. Масштабирования между профилями нет. В проект нельзя без подготовки смешивать страницы разных профилей.

Внутри страницы/popup — непосредственные элементы. Промежуточные визуальные группы контролов не поддержаны; фон карточки можно сделать отдельной shape_. Иконки вложены в состояния; Track/Fill/Thumb — в Slider. Обычные popup могут быть вложены в организационную popupgroup_. Рекомендуется избегать перекрытия интерактивных объектов: поведение касания на панели проверяется отдельно.

## 3. Назначения, ключи и ID

| Назначение | Что задаётся |
|---|---|
| Проект | Ключ, имя проекта, профиль |
| Страница / popup | Ключ, ID контейнера, имя проекта, профиль, способ показа; у popup — modal |
| Группа popup | Ключ и ID группы; участники находятся внутри Frame группы |
| Button, Level, Slider, Value | Ключ, ID объекта, управляющий ID Extron |
| Text, Image, Shape, Line, DateTime, Popup reference | Ключ, ID объекта; управляющего ID нет |
| Состояние | Роль, имя и ID состояния |
| Иконка / изображение | Путь PNG и имя ресурса; иконка также имеет ключ ресурса |

После префикса — латинские буквы, цифры, точки и дефисы между непустыми частями; первый символ — буква. Без пробелов и дополнительных `_`. В текущем preview `button_side.hall` сохраняет имя и получает ключ `home.side.hall`; `SideHall` необязателен. Видимый текст может быть русским. `button_VolumeUp`, `button_volumeup`, `btn_VOLUMEUP` дают один новый ключ `home.volumeup`. Для нескольких зон: `button_HallVolumeUp`, `slider_TerraceVolume`. Старые сохранённые ключи при переименовании не меняются.

Ключ — постоянное смысловое обозначение до 100 символов: строчные латинские буквы/цифры, сегменты через `.`/`-`, первый символ — буква. Ключи контейнеров, элементов, групп и ресурсов уникальны во всём пакете. Один ресурс можно использовать повторно только с теми же объявлениями и PNG-байтами.

| ID | Диапазон и уникальность |
|---|---|
| ID страницы/popup | 1..65534, общее пространство контейнеров; 65535 зарезервирован Offline |
| ID группы popup | 1..65535, отдельное пространство |
| ID объекта элемента | 1..1000000, уникален внутри страницы/popup |
| Управляющий ID | 1..65535, уникален во всём проекте среди Button, Level, Slider, Value |
| ID состояния | 0..7; плотная последовательность от 0, сохраняется на состоянии |

Новые objectId начинаются с 1, controlId — с 8101, контейнеры проекта — со 100, группы — с 1; счётчики поднимаются выше существующих назначений. Сохранённые назначения имеют приоритет над именами. Резерв автоматически выданных ID сохраняется после удаления; номера не выдаются повторно. Это не полная история ручных ID/ключей. Для независимо подготовленных файлов совпадение ID не обещается.

Копия назначенного узла отклоняется по ownerNodeId: ей явно задаются собственные назначения, включая состояния/иконки. При ошибке записи плагин пытается восстановить все прежние metadata; при неполном восстановлении сообщает об этом и сохраняет резерв ID. При аварии возможны пропуски и частично записанные назначения; повторное распознавание их учитывает. Атомарность нескольких записей Figma не заявляется.

## 4. Кнопки и состояния

Внешний контейнер кнопки — **Group или Frame**; внешний Frame не имеет fills. Внутри 2–8 Group/Frame состояний, каждый `[0, 0, ширина кнопки, высота кнопки]`. Видимо ровно одно состояние для предпросмотра; экспортируются все, включая скрытые. Количество ограничено выбранным типом кнопки ниже.

**Локальный preview: оформление кнопок.** Исходная кнопка может быть обычной группой или Frame без состояний. Вне экранов на текущей странице разместить Button Styles с обычным/активным образцами или явно назначить их в дополнительных настройках плагина. Выбрать экран → «Оформление кнопок → Применить оформление»: button_/btn_ → Off/On, feedbackbutton_/fbtn_ → Normal/Active. Если есть готовые кнопки, плагин сначала требует явно выбрать пропуск или обновление; фон готовых normal/feedback состояний меняется только по выбору. Переносятся заливка и обводка, скругление — по настройке; иконки, подписи, ID и ручной Pressed сохраняются. Повторное применение не дублирует состояния; третье состояние рисуется вручную. [Структура, назначение фона и ограничения](BUTTON_STATES.md).

Group/Frame с прямоугольником фона экспортируются как составное оформление в PNG; произвольные подписи сохраняют свой вид в PNG. Поддержанный верхний Text на всю площадь может остаться нативным. Следующие требования к одному Text и одной Frame-иконке относятся к прежней нативной схеме Frame состояния.

### Единое правило для новых макетов

| Назначение | Состояния | Префикс |
|---|---|---|
| Включение или выбор | **Off / On** | `button_` / `btn_` |
| Нажатие и удержание | **Normal / Pressed** | `button_` / `btn_` |
| Выбор с отдельным видом нажатия | **Normal / Active / Pressed** | `feedbackbutton_` / `fbtn_` |

Схема задаёт единые имена для нового дизайна. Passive / Active, Normal / Active без Pressed и другие поддержанные синонимы остаются совместимыми. Готовые состояния, их имена и ID автоматически не меняются. По эталонам создаются только Off / On либо Normal / Active; Normal / Pressed подготавливается вручную, Pressed для тройки также добавляется вручную.

### Поддержанные кнопки с явным типом

| Префикс / тип в форме | Обязательные состояния | Роли / ID в GDL |
|---|---|---|
| `button_` / `btn_` · 2 состояния | **Off / On**, **Passive / Active** или **Normal / Pressed**, ровно 2 | normal = 0; feedback = 1 без press feedback; для Normal / Pressed пакетные ID 0/1, press feedback = 1 |
| `feedbackbutton_` / `fbtn_` · С выбором | **Normal / Active**, **Passive / Active** или **Off / On**, необязательный **Pressed** | normal = 0; feedback = 1; при наличии Pressed его ID = 2 и press feedback = 2, иначе −1 |

Регистр не важен; допустимы `st_Off`, `state_On`, `state_Active` и другие префиксы состояния. В пакете сохраняются имена без `st_`/`state_`. Normal / Off / Passive — синонимы роли normal; On / Active / Feedback — синонимы роли feedback. Для новых кнопок допустим один normal и один feedback либо pressed у обычной; у feedback-кнопки один normal, один feedback и необязательный pressed. Визуальные состояния рисует дизайнер. Плагин экспортирует только существующие состояния: отсутствующий Pressed и его PNG не создаются, скрытые существующие состояния экспортируются. Неверный набор блокирует распознавание/экспорт. On и Active обновляет программа управления; автоматического переключения/AV-команд не создаётся. Архив 0.2.2 сохраняет прежние строгие наборы; эти расширения требуют обновлённого плагина 0.3.2 preview.

Тип можно выбрать вручную в поле **«Тип кнопки»**. Переключение типа не меняет её objectId/controlId. У уже сохранённой кнопки прежних версий выбран пункт «Сохранённая · прежние состояния»; распознавание сохраняет её metadata и ID. Одно переименование `button_` в `fbtn_` сохранённый тип не меняет. Для явного перехода выбрать новый тип, затем согласовать назначения состояний: роль, имя и ID; слои состояний не удаляются сами. Имена уже назначенных состояний меняются через поле «Имя состояния», а не только переименованием слоя.

Новые типы хранят `buttonMode` в **exui-node/3**. Плагин 0.2.1 и старее их отклоняет; старые exui-node/1 и /2 продолжают читаться без миграции. Новые кнопки экспортируются как обычный native Button в exui/5. Для пакетов до 16 PNG подходит CLI 0.2.1; для большего числа PNG нужен обновлённый CLI 0.3.0 preview. В обновлённом exui/5 отдельного предела количества PNG нет; сохраняются ограничения PNG до 4 MiB, распакованного пакета до 16 MiB, manifest.json до 64 KiB и screen.json до 256 KiB. Прежние форматы сохраняют предел 16 PNG. Metadata и структура полей EXUI не меняются.

### Прежние сохранённые назначения

Следующая таблица описывает совместимость уже подготовленных кнопок без buttonMode, включая произвольные feedback-состояния. Новые типы ограничены наборами выше. Старые состояния и ID автоматически не переписываются.

| Схема | Применение |
|---|---|
| Normal / Pressed | «+»/«−»: Pressed пока держат, возврат при отпускании |
| Off / On | Устойчивое состояние от программы без отдельного вида нажатия |
| Off / On / Pressed | Обратная связь устройства плюс эффект удержания |
| Normal / state_Ready / state_Error / … / необязательный Pressed | Несколько feedback-состояний, максимум 8 всего |

Normal и Off — одна роль; On и Feedback — одна роль. Нельзя дублировать Normal/Off или On/Feedback. Дополнительные виды именуются `st_Ready` / `state_Ready`, `st_Error` / `state_Error`, `state_Disabled` и т. п. Это роль feedback. Первый ID 0 — normal, остальные — feedback или один pressed. ID берутся из metadata, порядок слоёв их не меняет. При удалении состояния с образованием пропуска нужно явно пересохранить согласованные ID в форме; плагин не меняет программные номера молча.

Внутри каждого состояния ровно один Text на всю кнопку, CENTER по горизонтали, CENTER/BOTTOM по вертикали; один общий шрифт для всех состояний. Одна непрозрачная SOLID-заливка, необязательная одна PNG-иконка. Виды должны различаться текстом, цветом или изображением; одного выравнивания недостаточно.

Начиная с плагина 0.2.1 в exui/5 Text состояния Button может содержать ровно пустую строку `""`. Это кнопка без собственной видимой подписи; Text сохраняется как носитель шрифта и геометрии. Пробельные строки запрещены. Видимые подписи можно сделать отдельными text_/value_ поверх кнопки на странице, в исходных координатах и выше кнопки по слоям. Они остаются редактируемыми, Value получает собственный controlId. Цвет и состояния этих подписей не следуют за состояниями кнопки автоматически; используйте читаемые сочетания и проверяйте касания/перекрытия на оборудовании. Для этого расширения нужны плагин и CLI 0.2.1; архив 0.2.0 его не содержит. Пустые Label/Value и состояния Multistate Level по-прежнему запрещены; exui/1–4 не меняются.

Жёлтый Pressed рисует дизайнер, например #FFCC00: имя само не перекрашивает кнопку. Для предпросмотра выбрать состояние по имени/ID и нажать «Показать состояние»; при нескольких feedback можно выбрать каждое отдельно. В прежней схеме Figma normal/feedback/pressed имеют canonical ID 0/1/2. Двухсостояниевой Normal/Pressed при экспорте соответствует плотная пара 0/1, сохранённые metadata при этом не меняются.

state_Disabled задаёт внешний вид. Блокировку нажатия выполняет программа управления. Mute, выбор источника и переключатель остаются Button с нужными состояниями и feedback.

## 5. Текст, изображения и оформление

Нативный текст: Arial Regular/Bold, Inter и Inter Display. Для Inter поддержаны девять весов Thin…Black и их курсивы; семейство встроено в GDL из закреплённой коллекции CLI. Размер `pt = px × 0.75`, 4..200 pt; одна непрозрачная SOLID-заливка, без text decoration, text case и letter spacing. Label/Value/DateTime поддерживают все комбинации Left/Center/Right и Top/Center/Bottom. До 256 единиц UTF-16, без NUL и повреждённого Unicode.

Смешанные шрифты, произвольные variable-оси, другие семейства, сложное оформление и дробная геометрия статических txt_/text_ сохраняются в PNG/PBImage без ручного Frame. Value/DateTime не превращаются в PNG: неподдержанное нативное оформление требует исправления. Для Button полный верхний Text на всю площадь с Center/Center либо Center/Bottom остаётся текстом самой кнопки. Одинаковые Inter-подписи в другом прямоугольнике всех состояний автоматически выносятся в один нативный Label; изменяющиеся или сложные подписи остаются в PNG. [Подробные условия](NATIVE_TEXT.md).

text_ — статичная подпись без управляющего ID. value_ — адресуемый PBLabel с начальным текстом и dynamicText; актуальное значение сообщает программа управления. Имя value_Volume не создаёт связь с Slider автоматически. datetime_ — Text с форматом времени, например `HH:mm` или `dd.MM.yyyy HH:mm`; в GDL это PBDateTime, а не статичная подпись. Часовой пояс и фактическое время проверить в настройках GUI Designer/панели.

Эффекты, маски, gradients, opacity узла, произвольные blend modes и prototype interactions не поддержаны. Режим NORMAL/PASS_THROUGH, opacity 100%, элементы видимы; исключение — скрытые состояния. Скругления и обводки допустимы только в перечисленных ниже нативных частях или внутри растеризуемых изображений/иконок.

logo_/img_/image_ — отдельный Frame → один PNG Native 1× с прозрачностью → PBImage без controlId, состояний и нажатия. Внешний Frame без эффектов, скруглений и обводки; его fills можно убрать для прозрачного фона. Внутри допустимы векторы, текст и другая графика: она растрируется, внутренние части отдельно не редактируются. Для кликабельного логотипа использовать Button с иконкой в состоянии. Дробные координаты и размеры графики и статического текста сохраняются: PNG получает целые внешние границы и прозрачные поля, без округления или масштабирования исходного слоя.

Иконка — Frame `Icon`, `ico_Name`, `icon_Name` внутри состояния. Native-размер не превышает кнопку; по центру по горизонтали, сверху или посередине по вертикали. PNG должен точно совпадать с размером Frame, включая прозрачные поля. Оформление её содержимого может быть сложным.

В обновлённом exui/5 отдельного лимита числа PNG нет; каждый до 4 MiB и 4096×4096, распакованный пакет до 16 MiB, manifest.json до 64 KiB, screen.json до 256 KiB. Для более чем 16 PNG нужен CLI 0.3.0 preview; прежние EXUI 1–4 сохраняют предел 16 PNG. Пути `assets/name.png`: строчные латинские буквы, цифры, дефисы, до 64 символов имени; resourceName — уникальное без учёта регистра ASCII-имя до 100 символов с `.png`. Имя слоя с точками не используется как имя файла PNG: пути ресурсов назначаются по ID. Один ключ с разными PNG запрещён. Ошибка PNG, превышение объёма изображений или изменение дизайна во время рендера прерывает экспорт.

## 6. Новые нативные элементы

| Тип | Подготовка и свойства |
|---|---|
| Level / Gauge / Indicator / Volume LED | Пустой Frame с SOLID fill. Направление и диапазон через форму, по умолчанию 0–100 слева направо. indicator_ — Gauge, отдельную лампу не создаёт. |
| Multistate Level | Frame без fills с 2–8 состояниями как у кнопки; первый normal, остальные feedback, без Pressed. |
| Slider | Frame без fills, ровно Track/Fill/Thumb; подробный пример в [таблице](PREFIXES.md#кастомный-slider). |
| Shape | Пустой Frame/Rectangle/Ellipse с SOLID fill. Для прямоугольника единое скругление, не больше половины меньшей стороны. Одна SOLID-обводка INSIDE либо без обводки. |
| Line | С 0.3.4 горизонтальная/вертикальная Pen (Vector) или Line с SOLID Stroke CENTER. Либо пустой прямоугольный Frame/Rectangle без скругления и обводки. Меньшая сторона — толщина, большая задаёт направление и длину. |

Track и Fill — Frame/Rectangle без дочерних слоёв, обводок и эффектов; одна заливка, одинаковое скругление. Track занимает всю длину и центрирован поперёк Slider. Fill совпадает с толщиной и начинается от нужного края: слева/справа/сверху/снизу по направлению. Thumb — круглый Frame, прямоугольник без скругления или Ellipse; внутри Slider, по центру поперёк дорожки. Изображения дорожки/бегунка и сложные эффекты пока не входят в поддержанный вариант.

### Линии Pen Tool и Line Tool (0.3.4)

Назвать слой `line_Divider` или `ln_Divider` и разместить непосредственно в Frame страницы/popup. Для Pen нужен один открытый отрезок с двумя точками, без управляющих ручек Безье; для Line Tool используется длина и поворот. После поворота линия должна оставаться горизонтальной или вертикальной. Отражение допускается, масштабирование и skew — нет.

Цвет задаёт один непрозрачный SOLID Stroke, выравнивание CENTER, толщина — целое число 1..1280 px, строго меньше длины. Fill отсутствует, окончания NONE. Пунктир, стрелки, круглые окончания, кривые, ломаные, замкнутые контуры, диагонали, переменная толщина, кисти и эффекты отклоняются с объяснением. Геометрия и исходный слой не изменяются.

В EXUI сохраняется прямоугольник окрашенной области, а не нулевая высота/ширина пути. Края Stroke и длина должны быть на целых пикселях: горизонтальный отрезок от (20, 40) до (120, 40) толщиной 2 px даёт rect [20, 39, 100, 2]. При толщине 1 px ось y=40.5 даёт rect [20, 40, 100, 1]; для вертикали аналогично x. Линия вместе с толщиной должна помещаться на странице. Результат — редактируемый PBLine, без PNG и controlId; EXUI/5 и CLI 0.3.0 не меняются.

Позиция Thumb и длина Fill — предпросмотр Figma. Начальное и актуальное значение сообщает программа, а не положение нарисованного Thumb. Кнопки «+»/«−», Value и Slider — отдельные объекты с отдельными ID; шаг, удержание и их взаимосвязь программируются в Extron.

## 7. Страницы и popup

Каждая страница — отдельный Frame. В секции проекта или project_ Frame должен быть 1..16 страниц, до 32 popup, до 16 групп и до 256 элементов всего; в одном контейнере 1..64 элемента. Фон страницы/popup — одна непрозрачная SOLID-заливка. Ровно одна страница стартовая; остальные показываются программой или по кнопке, указанной в карте ID.

Обычный popup имеет собственный размер и хотя бы одно место popupref на странице. Размер ссылки равен размеру popup; ссылка указывает либо ключ popup без группы, либо ключ группы. В группе обычные popup одного размера, группа непустая. Модальный popup полноэкранный, без группы; ссылки на него создаёт штатный Build. Popup reference внутри popup не поддержан.

Имена страниц/popup в пакете уникальны вместе с `Offline Page`. В 0.3.5 одинаковые имена фреймов различаются суффиксом в пакете; слои Figma не переименовываются. Переход у кнопки задаётся ключом page/popup и не ведёт к собственному контейнеру. «По кнопке» требует хотя бы одну ведущую кнопку. Переходы не пишутся как действия GDL: программа показывает контейнер по имени из актуальной карты ID. Команда `id-map` выдаёт назначенные ID, состояния и эти указания.

## 8. Поведение, совместимость и ограничения

Группа выбора, начальные доступность/видимость — указания в карте ID для программы управления; GDL сам их не исполняет. Указания доступны адресуемым Button/Level/Slider/Value, группа выбора — только Button. В Figma объект для экспорта остаётся видимым; пожелание скрыть его при запуске задаётся формой.

Видео и динамические изображения зарезервированы в таблице, но для профилей TLP Pro 1025M/300M отклоняются явно. Их не заменяют статичной картинкой молча. Поддержка других платформ — отдельное расширение с эталонами и проверкой.

Назначения хранятся под прежним private pluginData-ключом `exui`: старые — `exui-node/1`, расширенные типы/поля — `exui-node/2`, явные типы кнопок — `exui-node/3`. Старые назначения при распознавании сохраняются побайтово. Плагин 0.1.5 не понимает metadata/2: для нового макета пользоваться 0.2.2. Стабильный plugin ID менять нельзя; переноса private metadata между разными plugin ID нет.

У отдельного экрана резерв `exui-id-registry/1`; у проекта — `exui-id-registry/2` с отдельными счётчиками контейнеров и групп. При включении ранее подготовленных экранов в проект учитываются их сохранённые счётчики. В 0.3.5 конфликтующие ID получают свободные значения при проверке и экспорте; прежние уникальные назначения сохраняются. Ручная смена типа или ID через форму — действие автора. После исправления совпадений использовать актуальную карту ID для программы управления.

exui/5 не меняет смысл exui/1–4. Старый CLI вправе отклонить новый пакет или обновлённое поле реестра доноров. Использовать текущий CLI вместе с текущим samples/donors.json. Повторная конвертация создаёт новый GDL и не сохраняет ручные правки предыдущего файла.
